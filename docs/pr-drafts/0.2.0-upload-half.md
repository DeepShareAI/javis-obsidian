## Why

0.1.x mirrors the Javis wiki into a vault in one direction only (§Background). The spec's
goal is the other direction. The user picks folders, and the notes in those folders
go into the wiki as sources. Edits re-distil them, and when a note leaves the
folders its contributions are undone (§Goals, §A).

A wrong DELETE here removes a user's note from every shared page it fed. The
client is therefore built fail-closed (§F.3, §L.5):

- Only absence from the vault listing counts toward a delete (§F.3.2).
- A note must be missed twice, at least five minutes apart (§F.3.3).
- A mass-change cap holds the deletes (§F.3.4).
- A suspicious edit is held (§F.3.5).
- Invalid folder selections are refused (§F.3.1).

The token model also moves. Every connect asks for the `/wiki` resource (§C.3).
Uploading needs `wiki:write`, which is obtained by a step-up only when a folder is
selected (§C.7).

## What changed

### 1. `src/core/`: pure decisions (no Obsidian, no clock, no I/O)

- `sha256.ts`: a synchronous FIPS 180-4 implementation, cross-checked against
  `node:crypto` in tests.
- `note-text.ts` produces the PUT's `text` with `uploadText`. It strips the BOM,
  normalizes line endings, removes top-level `javis_*` keys, and drops a
  frontmatter block that is empty after that removal (D-HASH-2). The file also has
  `noteHash` (`body_hash = sha256(utf8(text))`, D-HASH-5) and text-level readers for
  `javis_source_id` and `title`, plus `isWikiPageText`. Its frontmatter scanner is
  pinned to `extractFrontmatterBlock`.
- `stamp.ts`: `stampText` and `restampText` insert one line and leave every other
  byte as it was, using the file's own line ending. They refuse an unclosed fence
  and are idempotent.
- `folders.ts`: §F.3.1 validation. It is case-insensitive for wiki folders, the
  config folder, duplicates and nesting.
- `upload.ts`: `planUpload(local, server, memory, settings)` returns every §F.1
  action (`stamp`, `restamp`, `put` including `adopt`, `delete`), plus held,
  skipped and waiting entries, and applies every §F.3 guard.

### 2. `src/shell/`: the doing

- `sources-api.ts`: `GET`, `PUT` and `DELETE /wiki/sources/obsidian`. A malformed
  row fails the whole listing, because the listing drives deletes.
- `upload.ts`: `uploadOnce` enumerates notes and reads each one fresh with a 10 s
  timeout. It then plans, stamps before the PUT, and sends the PUTs and DELETEs,
  with 429 backoff and one step-up per run. It never throws.
  The file also has `SelfWriteTracker`, the edit debounce, `runDownloadThenUpload`,
  and the pure `uploadReport` builder.
- `auth.ts`:
  - `connectOptionsFor` sends `resource=<origin>/wiki` on every connect.
  - `grantedScopes` and `grantedAudiences` decode the token.
  - `lacksWriteGrant` decides the step-up.
  - Tokens are bound to the origin that issued them (`SECRET_TOKEN_ORIGIN`,
    `OriginChangedError`).
  - `accountKey` identifies the account.
- `origin.ts`: one loopback-or-https rule. It is used by the export URL, the
  sources URL, and every OAuth call.
- `settings-load.ts`: `sanitizeSettings`, a pure, tested repair of `data.json`.
  `clampMinutes` moved here.
- `vault.ts` gains `readFresh`, `processText` and `listNotesIn`. It still has no
  delete or trash, and a test now scans `src/` for either (the check covers
  `trashFile` and the adapter's remove APIs).
- `settings.ts`, `folder-suggest.ts` and `review-modal.ts` add the Upload section,
  the folder picker, the **Review pending changes** command, the list of
  server-side failures with `last_error`, and a "Start uploads over" reset.
- `contracts.ts` and `errors.ts` add the upload contracts, the settings fields, and
  run-level errors such as `AccountChangedError`.

### 3. `src/main.ts`

A run downloads, then uploads, inside the existing single-flight guard.
`syncNow(trigger)` keeps its signature. The debounce clocks (`missingSince`) are
kept per device in `app.saveLocalStorage`, and `data.json` always stores them as
`null`.

### 4. README, version

The README has the §F.5 upload disclosure: which notes leave the vault, where they

## Decisions a reviewer should check

The rationale for each is in the plan (§1 and the Amendments section). The judgment
calls:

- **D-AUTH-1 (changed in review).** Every connect sends `resource=/wiki`. The union
  scope is added only once a folder is selected. The original plan deferred the
  resource for read-only installs. An `/mcp`-audience grant cannot be moved by a
  refresh, so those installs would have broken when the one-release grace (§C.3)
  ends. Pre-PR 1 servers ignore the parameter.
- **D-RUN-3 (widened in review).** A token "cannot write" when its decodable scope
  lacks `wiki:write`, or when its decodable `aud` is not `/wiki`. An interactive
  run steps up before its first read, stamp or request. A background run reports
  `paused`. Undecodable tokens are tried anyway.
- **D-PLAN-4.** A note whose identity cannot be read keeps alive any row at its
  path. A note like that at no known path holds every delete
  (`unreadable-ambiguous`), but only when it may hide an id. A readable note with
  no id at an uncarried live row's path is treated as that row's note. If it is
  blank it is skipped. Otherwise the same id is written back (`adopt`) and the edit
  goes through the normal put and shrink checks.
- **D-PLAN-8 (changed in review).** An emptied note, or one that shrank by more
  than 80%, is always held (`suspicious-edit`) and counts toward the cap (§F.3.5, §H).
- **D-PLAN-13 / D-RUN-2.** Deselecting any folder removes its notes behind the
  debounce and the cap, including when the last folder is deselected. The upload
  half makes no requests only when no folder is selected *and* no upload is
  remembered.
- **D-PLAN-18 (added in review): only this vault's rows.** The listing is per
  account. A row counts as this vault's only when upload memory has it, from a PUT
  made here or from a readable note here that carries its id. Other rows are never
  deleted or adopted, and they do not count toward the cap. The cost is that a row
  whose note vanished while `data.json` was lost stays on the server. **For PR 3 or
  a later spec:** a per-vault id on PUT and a filtered GET would remove this
  heuristic.
- **Account binding (added in review).** `uploadAccount` (origin plus token `sub`)
  is set by the first upload. A run in another account stops before it sends
  anything, and so does a step-up that returns a different account. "Start uploads
  over" is the explicit reset, and it also clears the folder selection.
- **Behavior change from 0.1.x.** A download from a plain-http server on another
  machine now fails with a sentence asking for https. The reason is that the bearer
  can now hold `wiki:write`.

## Wire contract to confirm against PR 3 (D-WIRE-1..4)

- `GET /wiki/sources/obsidian` returns `200 {"sources": [Row], "counts": {status: n}}`.
  - `Row = {source_id, vault_path, body_hash (64 hex), status, deleted, last_error, undo_report}`.
  - The response has no paging.
- `PUT …/{uuid}` takes JSON `{vault_path, title, text, body_hash}` and answers:
  - 200 `unchanged`
  - 202 `accepted`
  - 400 with `detail`, which is shown to the user
  - 409
  - 413
- `DELETE …/{uuid}` answers 202 or 204.
- A 403 carries `WWW-Authenticate: Bearer error="insufficient_scope"`. **Ask of
  PR 3:** answer 403 `insufficient_scope`, not 401, to an old-audience token on these routes. The
  client treats a 401 as expiry. It pre-empts the step-up only for tokens it can
  decode.
- `body_hash` is the hash of exactly the `text` string that was sent. Notes that
  contain a lone UTF-16 surrogate are not uploaded.
- The README's privacy URL (`https://javis.is/privacy`) must match PR 3's privacy
  page.

## Migrations / deploy order

This PR has no migrations. The plugin stores no server-side state. The new local
state is:
- in `data.json`: `uploadFolders`, `uploadMemory`, `lastUpload`,
  `pendingReuploadIds`, `uploadRemovedIds` and `uploadAccount`
- in the device keychain: the token origin
- in device local storage: the debounce clocks

`sanitizeSettings` loads a 0.1.x `data.json` with defaults.

Order per §I:
1. javis-server PR 1 (OAuth hardening), then deploy javis-mcp.
2. PR 2 (contributions).
3. PR 3 (Obsidian ingest routes, poller, privacy page), then deploy.
4. This release: first a scratch vault, then a copy of the real vault, then the
   real vault.

A 0.2.0 install that never selects a folder makes the same kinds of requests as
0.1.x, except that its connect now asks for `resource=/wiki`.

## Risks

- **Wrong deletes remain the main risk.** It is mitigated by the listing-absence
  rule, the per-device two-miss debounce, the mass cap, suspicious-edit holds,
  D-PLAN-18 scoping and account binding. Server-side undo (§D.4) is the backstop.
- **D-PLAN-18 is a heuristic.** A row whose note disappears while `data.json` is
  lost stays on the server until a server-side per-vault id exists.
- **Undecodable tokens and 401.** If PR 3 answers 401 rather than 403 for an
  undecodable old-audience token, the client reports "reconnect" instead of
  stepping up.
- **Slow reads.** Reads are sequential with a 10 s timeout. A folder of many
  iCloud dataless files makes a run slow, but not unsafe.
- **http is now refused.** Users of a non-loopback plain-http server lose the
  download they had in 0.1.x.
